로그인 및 대기열 흐름 설명
    
  ---
  1. 로그인 흐름 (Phase 1)

  클라이언트 → Auth API → MySQL → Redis → 클라이언트

  1. 클라이언트가 HTTP POST로 로그인 요청을 보낸다. (auth/login)
  2. Auth API가 MySQL에서 유저 정보를 조회·검증한다.
  3. 검증 성공 시, Refresh Token을 Redis에 7일 TTL로 저장한다.
  4. 클라이언트에게 JWT 두 가지를 발급한다.
    - Access Token: 15분 유효 (API 요청 시 사용)
    - Refresh Token: 7일 유효 (Access Token 재발급 시 사용)

  ---
  2. 대기열 흐름 (Phase 2)

  클라이언트 → Ticket API → Redis(Sorted Set) → QueueWorker → 클라이언트

  1. 클라이언트가 HTTP POST로 대기열 진입을 요청한다. (http header 에 access_token)
  2. Ticket API가 Redis **Sorted Set(ZSet)**에 유저를 등록한다.
    - ZSet은 점수(타임스탬프)로 순서를 유지해 대기 순번을 자동 관리한다.
  3. 대기열 등록 성공 응답 받은 실시간 연결 방식에 따라 두 가지로 나뉜다.

  경로 A — SignalR (WebSocket, 기본)
  - 클라이언트가 /hubs/queue에 WebSocket 연결을 맺는다.
  - QueueWorker가 1초 주기로 Redis를 순회한다.
    - 응답 없는 유저(Ghost) 정리
    - 상위 N명을 "Active" 상태로 전환 (입장권 발급)
  - Active가 되면 서버가 Push 알림(QueueActivated)을 클라이언트에 즉시 전송한다.

  경로 B — 스마트 폴링 (SignalR 실패 시 Fallback)

  - 클라이언트가 HTTP GET으로 주기적으로 순위를 조회한다.
  - 서버가 현재 순위에 따라 **다음 폴링 간격(NextPollDelay)**을 응답으로 내려준다.
    - 순위가 낮을수록 폴링 간격을 길게 → 불필요한 요청 감소
  - Active 상태가 되면 클라이언트가 자발적으로 게임 서버로 진입한다.

  ---
  3. 게임 서버 진입 (Phase 3)

  1. 클라이언트가 TCP로 Game Server에 접속하고 JWT와 RoomId를 담은 C_Login 패킷을 전송한다.
  2. Game Server가 Redis에서 입장권(Active 키)을 검증 후 즉시 삭제한다.
    - 1회용 입장권 → 중복 진입 방지
  3. 성공 시 S_Login 응답과 함께 로비(광장)에 입장한다.

  ---


Ghost 유저 / 하트비트 / 분산 락 설명
  
  ---
  1. 하트비트 — "나 아직 살아있어요" 신호
  
  대기열에 들어온 유저가 중간에 앱을 꺼버리거나 네트워크가 끊겨도, 서버는 즉시 알 수가 없다. 
  이 문제를 해결하기 위해 하트비트를 사용한다.

  두 곳에서 하트비트를 갱신한다.
  대기열 진입 시 (/queue/enter) │ QueueController.cs:35 
  폴링 요청마다 (/queue/status) │ QueueController.cs:64

  결과적으로 클라이언트가 살아있는 한 계속 최신 타임스탬프로 갱신된다.
  SignalR 경로는 Push를 받으면 끝이므로 폴링이 없지만, 연결 자체가
  살아있으면 곧 Active가 되므로 하트비트가 없어도 큰 문제가 없다.

  ---
  2. Ghost 유저 — 아무 신호도 없이 사라진 유저

  하트비트가 60초 이상 갱신되지 않은 유저를 Ghost(유령)로 판단하고
  대기열에서 제거한다.

  왜 Lua 스크립트로 처리하는가? (Lock Free)
  HEARTBEATS와 QUEUE, 두 ZSet을 동시에 정리해야 한다. 별도 명령으로 나누면
  중간에 실패할 수 있으므로, Lua로 묶어 원자적으로 처리한다.

  ---
  3. 분산 락 — QueueWorker가 여러 대여도 1대만 작동

  API 서버는 여러 대(Scale-Out) 뜰 수 있고, 각 서버마다 QueueWorkerService가 실행된다. 
  아무 처리 없이 두면 여러 워커가 동시에 같은 유저를 Active 전환하는 문제가 생긴다.

  해결: Redis SET NX (분산 락) - 대기열 통과 처리시
  SET NX는 Redis가 원자적으로 처리하므로, 여러 서버가 동시에 시도해도 단 하나만 성공한다.
  
  ---
  4. 락 해제 시 내 락인지 확인하는 이유
   
  만약 TTL이 만료되어 락이 자동 해제된 뒤 다른 서버가 락을 가져간 상태에서,
  원래 서버가 뒤늦게 DEL을 하면 남의 락을 지우는 사고가 발생한다. 
  UUID 비교로 이를 방지한다.

  ---
  5. 락 TTL 자동 연장 (Lock Heartbeat)
  락은 10초 TTL로 발급되는데, 처리가 오래 걸리면 만료될 수 있다. 그래서 3초마다 TTL을 연장한다.

  ---
  6. 전체 흐름 요약

  워커 실행 (1초 주기)
      ↓
  분산 락 획득 시도 (SET NX)
      ├─ 실패 → 1초 대기 후 재시도
      └─ 성공 → 아래 작업 실행
             ↓
      Ghost 유저 정리 (하트비트 60초 초과자 제거)
             ↓
      대기열 상위 50명 pop → Active 키 발급 + SignalR Push
             ↓
      락 해제 (내 UUID 확인 후 DEL)



동시 로그인 처리에 대한 설명                              
  

  ---   
  Layer 1. IP별 과부하 차단 — Sliding Window Rate Limit
  동일 IP에서 로그인 요청이 폭발적으로 들어오는 것을 먼저 막는다.

  // AuthController.cs:33
  [RedisRateLimit("login")]
  [HttpPost("login")]

  -- RedisRateLimiterService.cs Lua 스크립트
  -- 윈도우(시간 범위) 밖의 오래된 요청 기록 제거
  redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now_ms - window_ms)
  -- 현재 윈도우 안의 요청 수 확인
  local count = redis.call('ZCARD', KEYS[1])
  if count >= limit then return 0 end  -- 초과 시 차단 (HTTP 429)
  -- 통과 시 현재 요청 기록 추가
  redis.call('ZADD', KEYS[1], now_ms, unique_id)

  Redis ZSet에 요청 시각을 점수로 기록해서, 최근 N초 내 요청 수를 계산한다.
  한계를 넘으면 즉시 429 Too Many Requests 반환.
  이 카운터가 Redis에 있으므로 Auth API 서버가 여러 대여도 카운터가
  공유된다.

  ---
  Layer 2. 대기열 중복 등록 방지 — ZADD NX

  같은 유저가 대기열에 두 번 들어오는 것을 막는다.

  -- QueueService.cs RegisterQueueAsync Lua 스크립트
  local added = redis.call('ZADD', KEYS[1], 'NX', score, userId)
  -- NX = 이미 존재하면 무시, 없을 때만 추가
  return added  -- 0이면 이미 등록된 유저

  ZADD NX는 이미 ZSet에 있는 유저를 재등록하지 않는다. 네트워크 끊김으로
  클라이언트가 /queue/enter를 두 번 보내도 순번이 바뀌지 않는다.
  
  
  ---
  Layer 3. 게임 서버 중복 접속 방지 — 분산 락

  같은 유저가 두 개의 TCP 연결로 동시에 게임 서버에 접속하는 것을 막는다.

  // PacketHandler.cs:196~210
  string lockKey = $"player:login_lock:{playerId}";
  string lockValue = await
  RedisManager.Instance.LockManager.AcquireLockAsync(
      lockKey,
      TimeSpan.FromDays(1),   // TTL: 접속 유지 시간만큼 락 유지
      TimeSpan.FromSeconds(1),
      TimeSpan.FromMilliseconds(100)
  );

  if (lockValue == null)  // 락 획득 실패 = 이미 다른 세션이 접속 중
  {
      await session.SendAsync(BuildS_LoginPacket(ResultDuplicate, 0));
      session.Disconnect();
      return;
  }

  락을 획득한 UUID는 세션 객체에 저장해두고, 접속이 끊길 때 자동으로
  해제된다.

  // GameSession.cs:77~82
  protected override void OnDisconnected(EndPoint endPoint)
  {
      if (SessionId > 0 && !string.IsNullOrEmpty(LoginLockValue))
      {
          string lockKey = $"player:login_lock:{SessionId}";
          _ = RedisManager.Instance.LockManager.ReleaseLockAsync(lockKey,
  LoginLockValue);
      }
  }


  ---
  4. 전체 흐름 요약
 
  로그인 요청 (HTTP)
      ↓
  [Layer 1] IP별 Rate Limit — 초당 N회 초과 시 429 차단
      ↓
  Auth API → JWT 발급
      ↓
  대기열 진입 요청
      ↓
  [Layer 2] ZADD NX — 동일 유저 중복 등록 무시
      ↓
  대기열 통과 → 게임 서버 TCP 접속
      ↓
  [Layer 3] SET NX 분산 락 — 동시 접속 시 두 번째 연결 즉시 차단
      접속 종료 시 → 락 자동 해제 (OnDisconnected)



  이 프로젝트에서 두 방식이 쓰이는 곳 (Lock Free, 분산락)
  ┌──────────────┬─────────────────────────────┬────────────────────────┐
  │     방식     │          사용 위치          │          이유          │
  ├──────────────┼─────────────────────────────┼────────────────────────┤
  │ 분산 락 (SET │ QueueWorker 리더 선출, 게임 │ 작업이 진행 중인 동안  │
  │  NX)         │  서버 중복 로그인 차단      │ 계속 점유가 필요       │
  ├──────────────┼─────────────────────────────┼────────────────────────┤
  │ 락프리 (Lua  │ Refresh Token GET+DEL,      │ 단발성 연산이라 락     │
  │ 원자 연산)   │ 대기열 등록 ZADD NX, Rate   │ 없이 원자성만 보장하면 │
  │              │ Limit                       │  충분                  │
  └──────────────┴─────────────────────────────┴────────────────────────┘

  한 줄 요약:
  - 분산 락 = "여러 서버 중 1대만 작업하도록 Redis로 조율"
  - 락프리 = "락 없이 원자적 연산으로 충돌 자체를 없앰"
  - 둘 다 동시성 문제를 해결하지만, 분산 락은 점유/대기, 락프리는
  재시도/충돌회피 방식이다.
