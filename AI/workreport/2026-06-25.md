### 2. 1000명 E2E 수정 버그 5건 (main 직접 커밋)

**버그 A — Redis Lua 매칭 레이스 컨디션** (`GameMatchService.cs`)

`POP_TWO_SCRIPT`는 "큐에 2명이 있어야 pop"하는 구조로, 200명이 동시에 진입하면
모든 Lua 실행이 빈 큐를 보고 각자 ZADD만 하여 매칭이 전혀 발생하지 않는 근본 버그.
`MATCH_OR_QUEUE_SCRIPT`로 pop-or-enqueue를 단일 원자 트랜잭션으로 통합.

**버그 B — Lobby → Matching.API HTTP/HTTPS 불일치** (`Game.Lobby/Program.cs`)

Lobby의 HttpClient 기본 URL이 `http://localhost:7002`였으나
Matching.API는 HTTPS 전용 기동 → SSL 핸드셰이크 실패로 매칭 불가.

**버그 C — ServiceManager Game.Gomoku 헬스체크 실패** (`ServiceManager.cs`)

`HttpListener`가 Windows 비관리자 환경에서 포트 7779에 바인딩 불가.
`TcpPort: 7778`로 전환하여 TCP 직접 체크로 우회.

**버그 D — MATCHING_API_BASE_URL 기본값 HTTP** (`Consts.cs`)

Stage 10 MatchRecord 검증 734건 전체 실패 원인.
DummyClient와 GomokuRoom 모두 `http://localhost:7002`로 요청해 400 응답.
기본값을 `https://localhost:7002`로 수정.

**버그 E — GomokuRoom._httpClient SSL 미설정** (`GomokuRoom.cs`)

게임 결과 보고(`/api/gamematch/result`)와 시작 알림(`/api/gamematch/start`)이
자체 서명 인증서 검증 실패로 무음(fire-and-forget) 실패 중이었음.
`DangerousAcceptAnyServerCertificateValidator` 핸들러 추가.

> 버그 D·E는 게임 흐름을 차단하지 않는 fire-and-forget 패턴이라
> 단위 테스트나 소규모 검증으로는 절대 발견 불가능한 종류였다.

## 오늘 작업 피드백

### 1. E2E 테스트의 무음 버그 발굴 효과

**잘된 점**: 1000명 E2E 단 1회로 5건의 버그를 한꺼번에 확인했다.
특히 버그 D·E는 GomokuRoom이 Matching.API 보고 실패를 catch 후 `Console.WriteLine`만 하고 계속 진행해서,
게임 자체는 정상 작동처럼 보이지만 DB에는 아무 결과도 기록되지 않는 상태였다.
이런 무음 실패는 단위 테스트나 2명 시나리오로는 절대 드러나지 않는다.

**개선하면 좋을 점**: `fire-and-forget` HTTP 보고에 실패 로그 레벨을 `LogWarning` 이상으로 올리고,
Prometheus 등으로 실패율을 집계하면 E2E 없이도 운영 중 감지할 수 있다.

### 2. 원자적 Lua 스크립트 설계 원칙

**잘된 점**: `POP_TWO_SCRIPT`의 레이스 컨디션을 정확히 진단하고,
pop-or-enqueue를 단일 스크립트로 묶는 `MATCH_OR_QUEUE_SCRIPT` 패턴으로 올바르게 해결했다.
Redis Cluster에서 KEYS[1] 슬롯 고정도 함께 보장된다.

**개선하면 좋을 점**: Redis Lua 스크립트 도입 시 "N명 동시 호출" 시나리오를 설계 단계에서
검토하는 체크리스트가 있으면 좋겠다. 매칭처럼 상태 전이가 핵심인 로직은
초기 설계 때 경쟁 조건 분석을 별도 스텝으로 두는 것이 효과적이다.

### 3. 서비스 간 URL 관리 일관성

**잘된 점**: `MATCHING_API_BASE_URL`이 환경 변수 오버라이드 구조여서
기본값만 `https`로 바꾸면 로컬·도커·클라우드 환경이 동시에 해결됐다.

**개선하면 좋을 점**: Lobby를 HTTPS로 수정하고(PR #105) Consts.cs 기본값은 그대로 남겨뒀던 점이
이번 Stage 10 실패의 직접 원인이 됐다. 서비스 간 URL 상수를 변경할 때
소비자(GomokuRoom, DummyClient)까지 함께 검색하는 습관이 필요하다.

### 4. 작업 밀도와 범위 관리

**잘된 점**: Sprint #71~74까지 4개 스프린트를 이틀 안에 완주하며
Gomoku 게임 서버 완성 → E2E 준비 → E2E 자동화 → 운영 준비의
자연스러운 누적 흐름을 유지했다.

**개선하면 좋을 점**: E2E에서 발견된 버그 5건을 main에 직접 커밋했다.
규모가 작더라도 /plan → PR 흐름을 유지하면 이력 추적과 gate-check 적용이 가능해진다.
