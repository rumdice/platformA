- **SGameOver 패킷 개선**: `lobbyUrl` 필드 추가 (proto) — 클라이언트가 게임 종료 후 자동으로 로비로 복귀 가능

### 2. Gomoku E2E 준비 — 버그 5건 수정 및 시나리오 구현 (PR #105, 스프린트 #72)

PR #104 완성 후 전체 흐름 검증을 위한 준비 작업을 추가로 진행했다. 

- **Redis publish 안전성**: `GameMatchService.TryMatchAsync`의 Redis Pub/Sub publish 구간에 try/catch 추가 — 매칭 성사 알림 실패가 매칭 자체를 깨지 않도록 방어
- **구 폴링 루프 제거**: BackgroundService 내 `ProcessQueueAsync`/`ProcessMatchingAsync` 완전 제거 — game_transfer 티켓을 발급하지 않는 구 경로가 남아 있어 CLogin 실패를 유발하는 잠재적 버그 제거
- **gameType 검증**: `GomokuPacketHandler`에서 game_transfer 티켓의 gameType이 "gomoku"가 아니면 즉시 거부 — 잘못된 서버 접속 방지
- **MatchNotificationService 분리**: `OnMatchFound`의 인라인 `async void`를 `internal async Task ProcessMatchFoundAsync`로 분리 — 단위 테스트 가능성 확보
- **무승부 표시 수정**: `GetMatchHistoryAsync`에서 `WinnerId == null && Status == Completed`를 "미완료"가 아닌 "무승부"로 반환하는 버그 수정
- **TwoPlayerGomokuScenario**: DummyClient 시나리오 9번 구현 — Auth→Lobby SignalR→RequestMatch→MatchFound→Gomoku TCP→CLogin→자동 돌 놓기→SGameOver→MatchRecord 검증까지 전체 E2E 자동화
- **테스트 추가**: GameMatchControllerTests 2개 + MatchNotificationServiceTests 3개 → 전체 209개 통과

## 오늘 작업 피드백 및 개선점

### 1. 갭 분석 → 즉각 수정 루프의 효율성

**잘된 점**: gap analysis 문서를 기반으로 Sprint #71(Gomoku 완성)과 Sprint #72(E2E 준비)를 연속으로 실행하여 하루 만에 완성도를 65% → 95%로 끌어올렸다. 분석 → 계획 → 구현이 끊김 없이 이어진 좋은 사례다.

**개선하면 좋을 점**: gap analysis에서 발견된 "구 폴링 루프 잔존" 버그는 Sprint #71 범위에서 제거할 수 있었으나 Sprint #72로 미뤄졌다. 직접적인 버그는 같은 스프린트에서 처리하면 컨텍스트 전환 비용을 줄일 수 있다.

### 2. ProcessMatchFoundAsync 분리 — 테스트 가능성 설계 원칙

**잘된 점**: `async void`인 이벤트 핸들러를 `internal async Task`로 분리하는 패턴을 적용하여 `InternalsVisibleTo` + 직접 호출로 깔끔한 단위 테스트를 작성했다. 이 패턴은 다른 이벤트 핸들러에도 재사용 가능하다.

**개선하면 좋을 점**: `OnMatchFound`가 `async void` 패턴이었다는 것은 초기 설계 시 테스트 가능성을 고려하지 않았다는 의미다. 새 BackgroundService의 이벤트 핸들러는 처음부터 thin wrapper + testable method 패턴으로 작성하면 이후 리팩토링 비용을 줄일 수 있다.

### 3. E2E 시나리오의 구조 — TaskCompletionSource 패턴

**잘된 점**: `TwoPlayerGomokuScenario`에서 `TaskCompletionSource<MatchFoundInfo>`를 이용해 두 플레이어의 비동기 흐름을 깔끔하게 동기화했다. 각 플레이어가 독립적인 Task.Run으로 실행되면서도 MatchFound 이벤트를 안전하게 공유한다.

**개선하면 좋을 점**: 현재 E2E 시나리오는 DummyClient(수동 실행 도구)에만 있다. 이 로직을 `PlatformA.Tests.Integration` 프로젝트로 확장하면 CI에서 자동 회귀 테스트가 가능해진다. 물론 전체 서비스가 떠 있어야 하므로 docker-compose 환경 구성이 선행되어야 한다.

### 4. Utils.API 헬스체크 누락

**잘된 점**: 오늘 review 단계에서 Utils.API에 `/readyz` 헬스체크가 없다는 점을 체크리스트로 발견했다.

**개선하면 좋을 점**: Utils.API에 `/healthz` + `/readyz` 엔드포인트를 추가하는 작업을 다음 스프린트에 포함시키는 것이 좋다. 운영 환경에서 로드밸런서가 헬스체크를 사용하므로 미구현 상태는 배포 위험 요소다.

### 5. Library.Game 확장 필요

**잘된 점**: 공통 게임 로직(Board, 게임 인터페이스)을 Library.Game으로 분리한 기존 결정은 올바르다.

**개선하면 좋을 점**: 현재 Library.Game은 3개 파일밖에 없어 완성도가 낮다. 여러 게임 타입을 지원하려면 공통 인터페이스(IGameRoom, IGameSession, IGameResult)를 여기서 정의하고, Gomoku뿐 아니라 향후 게임들이 이를 구현하는 구조가 필요하다.
