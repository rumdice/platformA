#### MySQL DDL 이슈 해결 (레거시 Migration 수정)

  - `DROP INDEX IF EXISTS` 미사용으로 인한 재실패 → 전부 raw SQL `ALTER TABLE ... DROP INDEX IF EXISTS` 전환
  - `pid AUTO_INCREMENT` before PK 오류 → 순서 재정렬: NULL 업데이트 → NOT NULL 수정 → DROP INDEX → ADD PRIMARY KEY → AUTO_INCREMENT 부여
- MySQL DDL은 비트랜잭션이므로 부분 적용 상태에서 재실행 안전성을 `IF EXISTS` 패턴으로 보장

## 오늘 작업 피드백 및 개선점

### 1. MySQL DDL 비트랜잭션 특성 대응 패턴 확립

**잘된 점**: 4단계 오류를 단계적으로 분리 진단하여 `IF EXISTS` 패턴과 PK-before-AUTO_INCREMENT 순서 규칙을 실전에서 확립했다. 동일 Migration을 여러 번 재실행해도 안전한 멱등 SQL 패턴이 정착됐다.

**개선하면 좋을 점**: Migration 작성 전에 `SHOW CREATE TABLE` 또는 `DESCRIBE`로 실제 DB 상태를 먼저 확인하는 루틴을 추가하면 디버깅 사이클을 크게 단축할 수 있다. 향후 복잡한 Migration은 `db-migrator` 에이전트에 사전 검증을 맡기는 것이 좋다.

### 2. ELO fire-and-forget 설계의 트레이드오프

**잘된 점**: 게임 결과 저장과 ELO 업데이트를 분리하여 ELO 계산 실패가 매치 결과 저장을 막지 않도록 설계했다. 비동기 fire-and-forget으로 게임 종료 응답 레이턴시에 영향을 주지 않는다.

**개선하면 좋을 점**: ELO 업데이트 실패는 현재 아무런 알림 없이 묻힌다. `_logger.LogError`는 있지만 재시도 큐나 DLQ(Dead Letter Queue)가 없다. Redis에 실패 목록을 기록해 후처리하는 패턴을 고려할 수 있다.

### 3. MSB3492 병렬 빌드 캐시 충돌 반복 발생

**잘된 점**: `dotnet clean` 후 `-maxcpucount:1` 직렬 빌드 → 프로젝트별 개별 테스트 실행 패턴으로 안정적으로 우회했다.

**개선하면 좋을 점**: 이 오류는 세션 전환 후 반복 발생한다. `Directory.Build.props`에 `<BuildInParallel>false</BuildInParallel>` 또는 프로젝트 루트에 `dotnet.rsp` 파일로 `-maxcpucount:1`을 기본화하면 세션마다 같은 절차를 반복하지 않아도 된다.

### 4. Rate Limit 요구사항 범위 조정

**잘된 점**: Sprint #76 범위에 "IP→유저 기반 전환"이 포함되어 있었지만, 이를 구현 중 유저 기반 Rate Limit은 별도 Redis 키 설계와 JWT 클레임 추출 연동이 필요함을 파악하고 임계값 조정으로 범위를 명확히 제한했다. E2E 통과(10→100/분)라는 즉각적 목표는 달성됐다.

**개선하면 좋을 점**: `/plan` 단계에서 "유저 기반 Rate Limit"의 구현 복잡도를 사전 평가하여 처음부터 별도 스프린트로 분리했다면 더 명확한 Done 기준을 가질 수 있었다.

### 5. 컨텍스트 압축 이후 재개 처리

**잘된 점**: 이전 세션 컨텍스트 압축 후에도 `dotnet test` 재실행과 `db_write.py` 상태 갱신을 끊김 없이 재개했다. 세션 요약 덕분에 어느 단계에서 중단됐는지 즉시 파악 가능했다.

**개선하면 좋을 점**: 컨텍스트 압축이 발생할 수 있는 XL 규모 스프린트에서는 중간 상태를 DB step에 더 세밀하게 기록하면(예: "테스트 실행 중" step) 재개 시 중복 작업을 줄일 수 있다.
