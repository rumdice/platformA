## 오늘 작업 피드백 및 개선점

### 1. 작은 단위 수정 → 코드 이해 중심 접근

**잘된 점**: 오늘 작업(`GetPlayerRatingAsync` 단일 메서드 수정)은 사용자가 직접 코드를 분석하여 도출한 개선점으로, 변경 범위가 명확하고 테스트 4개가 4가지 경로를 모두 커버했다. Redis와 DB의 역할 분리(캐시 vs 영속) 개념을 직접 코드로 확인할 수 있는 좋은 학습 포인트였다.

**개선하면 좋을 점**: `GetPlayerRatingAsync`는 현재 매칭 요청마다 호출되는 hot path다. Redis miss 빈도가 높아지는 상황(서버 재시작, TTL 대량 만료)에서 DB 부하가 일시적으로 집중될 수 있다. 추후 cache warming 전략(게임 종료 시 rating 업데이트와 함께 TTL 연장)을 검토할 만하다.

### 2. xUnit Collection Fixture — 싱글톤 Mock 오염 패턴 발견

**잘된 점**: `RedisManager.Instance`가 프로세스 단위 싱글톤이라서 두 개의 `WebApplicationFactory`가 동시에 존재하면 mock 필드가 덮어씌워지는 문제를 test-writer 에이전트가 정확히 진단하고 `[Collection]` 패턴으로 해결했다. 이 패턴은 향후 Matching.API 테스트 추가 시 항상 적용해야 할 제약이다.

**개선하면 좋을 점**: `.claude/rules/tests.md`에 이 제약을 명시적으로 기록해두면 다음 테스트 작성 시 처음부터 올바른 구조로 시작할 수 있다. (현재는 현황 테이블만 업데이트됨)

### 3. 작업 방향 전환 — 기능 개발에서 코드 이해로

**잘된 점**: 오늘부터 새 기능 개발보다 개발자가 직접 코드를 분석하고 개선점을 도출하는 방식으로 전환한 것은 플랫폼 완성도가 88%에 도달한 시점에서 적절한 판단이다. 코드 장악력 없이 기능만 추가하면 이후 유지보수 비용이 급격히 증가한다.

**개선하면 좋을 점**: 리뷰 대상 코드를 선정할 때 "가장 자주 호출되는 경로"(`TryMatchAsync`, `GetPlayerRatingAsync`, JWT 검증 흐름)와 "가장 복잡한 상태 관리"(`GomokuRoom.Push()` 패턴)를 우선순위로 정하면 효과적이다.
