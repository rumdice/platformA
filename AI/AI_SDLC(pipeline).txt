## 스킬 워크플로 (전체 순서)

```
/plan {작업 설명}     → [Stage 1] 설명 분석 → PlanName 생성 → 브랜치 + task JSON 커밋 + SPRINT 등록
/requirement          → [Stage 2] 요구사항 상세 분석 + 명세 파일 브랜치 커밋 + DESIGN_REVIEW
/impact               → 영향 범위·위험도 분석 (코드 수정 전)
/start                → task 상태 coding 전환 + 명세 파일 기반 작업 지시서 출력
  (코딩)
/test-gen             → test-writer 에이전트 실행, 테스트 케이스 생성 (컨트롤러 변경 시 필수)
/done                 → 커밋 + 빌드 + 포맷 + 테스트 + push (반복 가능)
/pr                   → SPRINT 완료 체크 + PR 생성 + task done + cost-log
[GitHub Actions]      → sdlc-gate-check.yml  — PR 단계 SDLC 공정 자동 검사 (2차 방어선)
[GitHub Actions]      → pr-merge-sync.yml    — 머지 후 task JSON·SPRINT·cost-log 자동 동기화
```

스킬-단계 매핑:

| 단계 | 이름 | 스킬 / 실행 주체 |
|------|------|-----------------|
| 0 | USER_PLAN | — (Plan mode 또는 직접 입력) |
| 1 | PLAN_BRANCH + 계획 분석 | /plan (Stage 1: 설명 분석 → 브랜치·task JSON 생성) |
| 2 | REQUIREMENT_ANALYSIS + DESIGN_REVIEW | /requirement (Stage 2: 명세 브랜치 커밋) |
| 3 | IMPACT_ANALYSIS | /impact |
| 4 | CODE_FIX_START | /start |
| 5 | CODE_FIX | Claude Code 구현 |
| 6 | TEST_CASE_GENERATION | /test-gen |
| 7 | BUILD_TEST | /done |
| 8 | CODE_REVIEW | /review (HIGH 위험도 필수) |
| 9 | PR_SUMMARY | /pr |
| 10 | PR_GATE_CHECK | GitHub Actions sdlc-gate-check.yml (2차 방어선) |
| 11 | MERGE_SYNC | GitHub Actions pr-merge-sync.yml (사후 동기화) |

게이트 정책 (2026-05-30 강화):
- /plan: task JSON을 브랜치에 즉시 커밋 → gate-check가 PR 생성 시점에 반드시 탐지 가능
- /requirement: 명세 파일을 브랜치에 커밋 + task JSON steps[] 기록
- /test-gen: 소스 코드(.cs/.proto) 변경 시 /done 이전 실행 필수 (미실행 시 /done 차단)
- /impact: 코드 변경 시 /done 이전 실행 필수 (미실행 시 /done 차단, /pr도 차단)
- /review: 코드 변경 시 /done 이전 실행 필수 (미실행 시 /done 차단)
- /done: SDLC 사전검사(test-gen·impact·review) → BUILD_GATE (커밋→빌드→포맷→테스트→push)
- /pr: test_generated/review_completed/impact 필드를 task JSON에서 읽어 게이트 판단 (1차 방어선)
  ① test_generated=false + 코드 변경 → 차단
  ② review_completed=false + 고위험·다수변경 → 차단
  ③ impact=null + 코드 변경 → 차단 (경고 → 차단으로 강화)
- sdlc-gate-check.yml: PR 생성/수정 시 test/review/impact 공정 준수 자동 검사 (2차 방어선)
  - task JSON 없음 + 고위험 코드 변경 → FAIL (핫픽스/문서 제외)
  - task JSON 없음 + 일반 코드 변경 → WARNING
  - 코드 변경 + test_generated=false → FAIL
  - 고위험 경로 + impact=null 또는 review_completed=false → FAIL
- pr-merge-sync.yml: PR 머지 후 task JSON·SPRINT.md·cost-log 자동 갱신 (사후 보완)
  + PR closed without merge → task status: abandoned (신규, 2026-05-30)
- ci.yml: CI 빌드/포맷/테스트 실패 시 task JSON last_error 갱신 + PR 댓글 (신규, 2026-05-30)

작업 단계는 순차적으로 진행된다. (최종 업데이트: 2026-05-30, 스프린트 #31)

0. USER_PLAN  ←  /plan 스킬
기능 : 사용자가 작업 설명을 입력하면 LLM이 분석하여 계획을 수립하고, 브랜치와 task JSON을 생성한다.
→ /plan 스킬로 구현됨 (Stage 1)

  입력 방법:
  - /plan {작업 설명}   — 텍스트로 직접 입력
  - Plan mode 승인 후 /plan 실행 — LLM과 사전에 계획을 정제한 뒤 실행

  처리:
  - 사용자 설명을 분석하여 작업 목적·범위·구현 방향을 요약한다.
  - PascalCase PlanName 생성 (예: AddRedisRateLimit, FixAuthTokenExpiry)
  - 브랜치 생성: YYYY-MM-DD_PlanName
  - task JSON 생성 및 브랜치에 즉시 커밋 (gate-check가 PR 생성 시 탐지 가능하도록)
  - SPRINT.md 진행 중 섹션에 태스크 항목 추가 후 커밋

  산출물:
  - 브랜치: 2026-MM-DD_PlanName
  - AI/tasks/sprint{N}_{PlanName}.json (status: analyzing, steps: [plan])
  - AI/SPRINT.md 태스크 항목


1. REQUIREMENT_ANALYSIS + DESIGN_REVIEW  ←  /requirement 스킬
기능 : 브랜치 위에서 요구사항을 상세 분석하고 구현 명세 파일을 생성한다.
       기존 ADR과 대조하여 신규 아키텍처 결정이 필요한지 판정한다.
→ /requirement 스킬로 구현됨 (Stage 2, 2026-05-21 도입 / 2026-05-30 개선)

  전제: /plan으로 브랜치와 task JSON이 이미 존재해야 한다.

  소스 탐지 우선순위:
  1순위: .claude/plan/*.md       — 외부 제출 파일 (외부 Agent, 기획서 등)
  2순위: ~/.claude/plans/        — plan mode 임시 파일 (날짜 접두사 없는 파일만)
  3순위: task JSON의 plan summary — /plan에서 작성한 작업 목적 활용
  4순위: $ARGUMENTS              — 직접 입력 텍스트

  처리:
  - 요구사항 분석: 목적·범위·제약·오류/누락 체크 (불명확 시 사용자에게 질문)
  - 명세 파일 생성: .claude/plan/YYYY-MM-DD_NNN_PlanName.md
  - DESIGN_REVIEW: 기존 ADR(AI/adr/) 목록과 대조
    ✅ ADR 준수  → 진행
    ⚠️ ADR 충돌  → 사용자에게 보고 후 요구사항 조정
    📝 신규 ADR 필요  → task JSON의 adr_required = true 자동 갱신 + /adr 실행 안내 + 중단
  - 명세 파일과 소스 파일 처리를 브랜치에 커밋 (git add .claude/plan/ && git commit)
  - task JSON steps[]에 requirement 단계 기록

  ADR 자동 연계 구조:
  adr_required = true 설정 시:
    → /pr 게이트가 PR 생성을 차단한다 (1차 방어)
    → gate-check.yml이 GitHub Actions에서 FAIL한다 (2차 방어)
  해소 방법: /adr {주제} 실행 → task JSON adr_required = false 수정 → 진행

  산출물:
  - .claude/plan/YYYY-MM-DD_NNN_PlanName.md (브랜치에 커밋)
  - task JSON steps[]에 requirement 기록
  - task JSON adr_required: false(정상) / true(ADR 필요)


2. DESIGN_REVIEW
기능 : /requirement 단계에 내장됨 (별도 스킬 없음)
→ /requirement 스킬 5단계에서 수행
   - AI/adr/ 목록을 순회하여 요구사항과 대조
   - 신규 설계 결정이 필요하면 adr_required = true 자동 기록 후 /adr 연계
   - 신규 ADR 없이 PR 생성 불가 (로컬 /pr + GitHub Actions 양쪽에서 차단)


3. IMPACT_ANALYSIS  ←  /impact 스킬
기능 : 코드 수정 대상 파일·모듈을 파악하고 위험도·영향도를 평가한다.
→ /impact 스킬로 구현됨 (2026-05-21, 스프린트 #22)
   - /requirement 완료 보고에 다음 단계로 명시 (미실행 방지)
   - 사전 분석: 명세 파일 "영향 범위" 섹션 기반
   - 사후 분석: git diff 기반 (코드 수정 후 재실행 가능)
   - 결과를 task JSON impact 필드에 저장 (risk: LOW/MEDIUM/HIGH)


4. CODE_FIX_START  ←  /start 스킬
기능 : 코딩 시작을 선언하고 task 상태를 전환한다.
→ /start 스킬로 구현됨 (2026-05-21, 스프린트 #23)
   - task 상태 analyzing → coding 전환
   - 현재 브랜치의 명세 파일을 읽어 작업 지시서 출력
   - 명세 파일이 없으면 /requirement 실행을 안내하고 중단


5. CODE_FIX
기능 : 실제로 코드를 수정한다.
→ LLM이 /start 출력의 작업 지시서를 따라 자유롭게 구현


6. TEST_CASE_GENERATION  ←  /test-gen 스킬
기능 : 변경된 Controller/DTO/Service에 대한 xUnit 테스트를 자동 생성한다.
→ /test-gen 스킬로 구현됨 (2026-05-22, 스프린트 #24)
   - /start 이후, /done 이전 실행
   - 필수: 컨트롤러·DTO 변경 시 / 선택: 설정·인프라만 변경 시
   - test-writer 에이전트를 sub-agent로 실행 (기존 팩토리 패턴 재사용)
   - task JSON test_generated = true 기록


7. BUILD_TEST  ←  /done 스킬
기능 : 커밋 + 빌드 + 포맷 + 테스트 + push를 순서대로 실행한다.
→ /done 스킬로 구현됨 (2026-05-21 리팩토링)
   - BUILD_GATE만 담당 (PR 생성 없음 — 반복 실행 안전)
   - 빌드/테스트 실패 시 push 금지
   - task 상태 coding → testing 전환


8. QA_FAILURE_ANALYSIS  ←  /qa-failure 스킬
기능 : 빌드·테스트 실패 원인을 분석하고 재시도 여부를 판단한다.
→ /qa-failure 스킬로 구현됨 (2026-05-26, 스프린트 #28)
   - /done 실패 시 실행: GitHub Actions 실패 런 로그 자동 수집
   - BUILD / FORMAT / TEST 유형으로 분류
   - fixable_by_ai: true → 직접 수정 후 /done 재실행
   - fixable_by_ai: false → 원인·수동 수정 정보 제공
   - task JSON steps[]에 qa_failure 기록


9. PR_SUMMARY  ←  /pr 스킬
기능 : PR을 생성하고 SPRINT·task JSON·cost-log를 완료 처리한다.
→ /pr 스킬로 구현됨 (2026-05-21, 스프린트 #23 신규)
   - 1회만 실행 (PR 중복 방지 사전 검사 포함)
   - task 상태 testing → done 전환

   로컬 1차 방어선 게이트 (순서대로):
   ① task JSON 존재 여부 확인
   ② 코드 변경 여부 판별
   ③ test_generated == false + 코드 변경 → 차단
   ④ review_completed == false + 고위험·다수변경 → 차단
   ⑤ impact == null + 코드 변경 → 차단 (경고 → 차단으로 강화, 2026-05-30)
   ⑥ requirement steps 미실행 + 코드 변경 → 경고 (ADR 검토 생략 가능성)
   ⑦ adr_required == true → 차단 (/adr 실행 후 재시도)


10. PR_GATE_CHECK  ←  GitHub Actions sdlc-gate-check.yml
기능 : PR 단계 SDLC 공정 준수를 자동으로 검사한다.
→ GitHub Actions sdlc-gate-check.yml (2026-05-26, 스프린트 #27 신규 / 2026-05-30 강화)
   - 트리거: PR open/synchronize/reopened/ready_for_review
   - /pr 우회 또는 GitHub UI 직접 PR 생성 경로를 커버하는 2차 방어선

   검사 항목:
   ① task JSON 없음 + 고위험 코드 변경 → FAIL
   ② task JSON 없음 + 일반 코드 변경 → WARNING
   ③ adr_required == true → FAIL  ← 2026-05-30 추가
   ④ requirement 미실행 + 코드 변경 → WARNING  ← 2026-05-30 추가
   ⑤ test_generated == false + 코드 변경 → FAIL
   ⑥ impact == null + 고위험 경로 → FAIL
   ⑦ review_completed == false + 고위험 조건 → FAIL

   출력: GitHub Actions Job Summary에 마크다운 결과 기록


11. MERGE_SYNC  ←  GitHub Actions pr-merge-sync.yml
기능 : PR 머지 후 SDLC 상태를 자동으로 동기화한다.
→ GitHub Actions pr-merge-sync.yml (2026-05-22, 스프린트 #26 신규 / 스프린트 #27 강화)
   - 트리거: PR merge (pull_request closed + merged)
   - /pr 미실행 경로도 사후 보완 (단, task JSON이 브랜치에 있어야 탐지 가능)

   처리:
   - task JSON: status=done, completed_at, pr_url 갱신 + steps[]에 merge_sync 기록
   - SPRINT.md: 해당 스프린트 섹션 '- [ ]' → '- [x]' 체크
   - cost-log.md: 중복 방지 후 행 추가 (규모 S/M/L/XL 자동 판단)

   주의: task JSON이 PR 머지 시점에 main에 없으면 skip 발생
   → /plan이 task JSON을 브랜치에 즉시 커밋하므로 정상 워크플로에서는 항상 탐지 가능
